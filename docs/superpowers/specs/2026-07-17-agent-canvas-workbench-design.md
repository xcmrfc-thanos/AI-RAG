# Agent 画布工作台体验优化设计

## 一、背景与目标

当前 `/admin/agents` 已具备 React Flow 画布、Schema v1 双向转换、草稿保存、校验、发布和已发布版本试跑能力，但操作体验仍停留在“可用的 Schema 编辑器”：节点只能点击添加、属性需要手动应用、画布空间偏小、节点语义与运行轨迹不清晰，也无法直接调试当前草稿。

本次将管理页优化为接近 Dify / 扣子操作节奏的 Agent 工作台：

1. 选择工作流后直接进入大画布编排。
2. 从节点库拖拽或在线性链中快捷插入节点。
3. 在右侧即时配置节点，自动写回并保存草稿。
4. 不发布即可试运行当前草稿。
5. 在画布和调试抽屉中查看节点状态、输入、输出、耗时与错误。
6. 增加可复用当前系统真实接口的安全只读节点和开箱即用模板。

## 二、范围与约束

### 2.1 本轮范围

- 重构 Agent 管理页为顶部工作流栏、左节点库、中画布、右属性面板、底部调试抽屉。
- 支持拖拽添加、链中插入、自动布局、复制、删除、撤销和重做。
- 增加开始/结束画布虚拟节点。
- 增加线性连接即时约束和可理解的校验提示。
- 属性面板改为即时写回，增加自动保存状态和变量选择器。
- 增加草稿校验、草稿试运行和节点级运行轨迹。
- 第一批增加文档列表、分类列表、标签列表和文本模板节点。
- 提供知识库问答、指定文档总结、主题资料汇总三个模板。

### 2.2 保持不变

- 持久化工作流继续使用 `schemaVersion=1`。
- 后端继续使用唯一线性链执行模型，节点数上限保持 10。
- 发布版本继续不可变，普通用户 `/agent` 仍只能运行已发布版本。
- Tool 调用继续经过 Gateway 并透传终端用户 Token。
- Search、Document ACL、超时、审计、错误码与取消语义保持现有边界。

### 2.3 明确排除

- 条件分支、循环、并行 DAG、多 Agent 协作和人工审批。
- 任意 HTTP、任意 SQL、脚本执行和自定义代码节点。
- 创建、修改、发布、删除文档等高风险写节点。
- 未完成可见性过滤前的知识图谱和统计文档节点。

## 三、方案选择

### 3.1 备选方案

1. 保守增强：保留当前工作流列表和三栏编辑器，只增加拖拽与配置优化。改动较小，但画布空间仍被工作流列表和属性栏挤压。
2. Dify 式工作台：顶部切换工作流，左节点库、中间大画布、右即时配置、底部调试抽屉。编排、调试和发布形成连续闭环。
3. 全屏专业画布：所有面板浮动或按需展开，画布空间最大，但更适合复杂 DAG，对当前线性工作流过重。

### 3.2 选定方案

采用方案 2。它能解决当前最明显的空间、配置和调试问题，同时不要求先升级为完整 DAG 引擎。方案 3 中的快捷命令和浮动面板可以在后续复杂度真实增长后再评估。

## 四、工作台信息架构

### 4.1 顶部工作流栏

顶部承担工作流级操作：

- 工作流选择器和新建入口。
- 工作流名称、草稿状态和当前发布版本。
- 撤销、重做、自动布局和校验。
- 草稿试运行和发布。
- 保存状态：`未保存`、`保存中`、`已保存`、`保存失败`。

原左侧“我的工作流”列表移出画布区域，改成顶部选择器或独立弹层，避免长期占用横向空间。

### 4.2 左侧节点库

节点库支持：

- 按“输入输出、知识获取、数据转换、AI 处理”分组。
- 按中文名称、工具名和说明搜索。
- 拖拽节点到空白画布。
- 点击节点时添加到当前链末尾。
- 节点条目展示名称、简短用途和是否需要配置。

### 4.3 中间画布

画布是工作台主区域：

- 工作流默认从左向右排列。
- 连线上显示快捷插入按钮。
- 节点拖到连线附近时显示插入预览。
- 支持自动布局、适应画布、小地图和缩放。
- 空画布显示模板入口和“从左侧拖入节点”的操作指引。
- 当前仍只允许唯一线性链，前端在创建边时即时阻止非法连接。

### 4.4 右侧属性面板

属性面板根据节点元数据渲染表单：

- 节点名称和节点 ID。
- 常用字段表单、字段说明、默认值和取值范围。
- 上游变量选择器。
- 节点输出字段说明。
- 高级 JSON 收入折叠区，不再作为主要配置方式。

字段修改后通过短延迟写回本地 Schema，不再要求点击“应用到节点”。草稿保存采用防抖请求，保存失败保留本地状态并允许重试。

### 4.5 底部调试抽屉

调试抽屉默认折叠，试运行后自动展开摘要：

- Run 状态、总耗时、开始和结束时间。
- 节点步骤状态和耗时。
- 当前选中节点的输入快照、输出快照和错误信息。
- 取消运行操作及“当前节点结束后生效”的提示。

Run Step 通过 `nodeId` 映射到画布节点，节点展示等待、运行中、成功、失败和取消状态。

## 五、节点模型

### 5.1 画布虚拟节点

#### 开始节点

开始节点用于声明 Run 输入字段，例如：

```json
{
  "query": { "type": "string", "required": true, "label": "用户问题" },
  "documentId": { "type": "number", "required": false, "label": "文档 ID" }
}
```

开始节点不作为后端执行步骤持久化。画布导出 Schema v1 时，输入声明写入工作流根对象的可选 `inputSchema` 扩展字段；旧定义没有该字段时继续按自由对象处理。

#### 结束节点

结束节点用于选择最终输出字段和展示名称。它不作为后端执行步骤；工作流仍以最后一个真实节点输出作为 Run `outputJson`。前端根据结束节点映射选择需要展示的字段。

为了保持旧 Schema 可运行，开始和结束节点的画布元数据保存在工作流根对象可选的 `uiSchema` 字段中，不进入 `nodes` 和 `edges` 执行集合。后端解析器忽略未知根字段。

### 5.2 第一批真实节点

#### 混合检索 `hybrid_search`

- 接口：`POST /api/search`
- 输入：`query`、`mode`、`topK`
- 输出：`query`、`mode`、`topK`、`hits`、`hitCount`、`untrustedCorpus`
- 安全：沿用 Search ACL，检索摘要按不可信数据包装。

#### 读取文档 `get_document`

- 接口：`GET /api/document/documents/{documentId}`
- 输入：`documentId`、`maxChars`
- 输出：`documentId`、`title`、`content`、`truncated`、`maxChars`、`untrustedContent`
- 安全：沿用 Document ACL，正文按不可信数据包装。

#### 文档列表 `list_documents`

- 接口：`GET /api/document/documents/page`
- 输入：`keyword`、`categoryId`、`teamId`、`status`、`sortBy`、`sortOrder`、`size`
- 约束：`size` 为 1～20，固定从第一页读取；不接受任意分页抓取。
- 输出：`documents`、`total`、`count`、`untrustedCorpus`
- 文档项仅保留 `id`、`title`、`summary`、`categoryId`、`categoryName`、`authorId`、`authorName`、`publishTime`。
- 安全：沿用文档分页查询的用户可见范围；摘要按不可信数据包装。

#### 分类列表 `list_categories`

- 接口：`GET /api/document/categories/tree`
- 输入：无。
- 输出：`categories`、`flatCategories`、`count`。
- 分类项保留 `id`、`name`、`description`、`parentId`、`documentCount` 和 `children`。

#### 标签列表 `list_tags`

- 接口：无 `categoryId` 时调用 `GET /api/document/api/tags/hot`；有 `categoryId` 时调用 `GET /api/document/api/tags/category/{categoryId}`。
- 输入：`categoryId`（可选）、`limit`。
- 约束：`limit` 为 1～50。
- 输出：`tags`、`count`。
- 标签项保留 `id`、`tagName`、`tagCode`、`categoryId`、`categoryName`、`docCount`。

#### 文本模板 `text_template`

- 执行位置：`kb-agent` 内部安全工具，不调用外部 HTTP。
- 输入：包含工作流变量引用的 `template`；变量由统一的 `VariableResolver` 在 Tool 执行前展开。
- 输出：`text`。
- Tool 只输出已经展开的文本，不维护第二套模板表达式，也不执行脚本、条件和循环。

#### 大模型处理 `llm`

- 保持 Schema `type=llm`，展示名称从“大模型回答”改为“大模型处理”。
- 输入：`prompt`。
- 输出：`text`、`model`、`stub`。
- 用途文案覆盖问答、总结、提取、改写和分类，不引入可由工作流覆盖的系统安全提示。

### 5.3 延后节点

以下节点不进入第一批：

- `graph_search`、`graph_relations`：现有 GraphController 未按终端用户过滤关联文档，需先增加文档可见性过滤和双用户 ACL 测试。
- `hot_documents`、`latest_documents`：Statistics 使用全局投影和缓存，可能返回当前用户无权查看的文档元数据；需改为按可见范围过滤或限定管理员使用。

## 六、变量与数据流

### 6.1 当前限制

当前只支持：

```text
${input.query}
${steps.search.output}
```

用户无法直接选择节点输出中的 `text`、`hits[0].documentId` 等字段，新增节点后仍然难以串联。

### 6.2 新变量语法

增加只读字段路径和数字下标：

```text
${input.query}
${steps.search.output.hits}
${steps.search.output.hits[0].documentId}
${steps.answer.output.text}
```

解析规则：

- 根仅允许 `input` 和 `steps`。
- `steps` 后必须是已成功的上游节点 ID。
- `output` 后只允许标识符字段和非负数字下标。
- 禁止方法调用、运算符、通配符、递归查询和任意表达式。
- 完整字符串只有一个变量时保留原对象类型；嵌入普通文本时序列化为字符串。
- 字段或下标不存在时以 `VALIDATION_ERROR` 失败，并指出具体路径。

### 6.3 前端变量选择器

节点目录元数据声明每个节点的输出 Schema。属性面板按拓扑顺序只展示当前节点之前的节点输出，避免引用下游或未连接节点。用户点击字段即可插入变量，不要求记忆语法。

## 七、线性图交互规则

前端和后端使用相同规则：

- 真实执行节点必须组成唯一线性链。
- 每个节点最多一个输入边和一个输出边。
- 不允许自环、反向边、重复边、孤立节点和不连通片段。
- 开始节点只能有输出，结束节点只能有输入。
- 删除中间节点时默认连接其前后节点；用户可选择只删除并留下断链。
- 拖节点到连线时，原边替换为“前节点 → 新节点 → 后节点”。
- 连接失败时不静默丢弃操作，画布展示具体原因。

## 八、草稿试运行

### 8.1 API 设计

新增管理员接口：

```text
POST /api/agent/workflows/{workflowId}/draft-runs
```

请求：

```json
{
  "definitionJson": "当前前端草稿 JSON",
  "input": { "query": "测试问题" },
  "idempotencyKey": "可选"
}
```

服务端处理：

1. 校验调用者拥有该工作流且具备 `agent:workflow:edit`。
2. 校验请求中的定义与当前工作流 Schema 规则一致。
3. 创建标记为草稿试运行的 Run 快照，不创建发布版本、不修改 `publishedVersionId`。
4. 使用请求定义的不可变快照执行，后续编辑不影响已开始的 Run。
5. Run 和 Step 继续写入现有审计表，并明确记录 `runSource=DRAFT`。

普通用户页面不开放草稿试运行接口。

### 8.2 运行轨迹

草稿 Run 返回现有 `AgentRunView`，Step 查询继续使用：

```text
GET /api/agent/runs/{runId}/steps
```

前端在 Run 终态前按受控间隔刷新 Run 和 Step；当前后端同步执行时可直接获取终态，但前端状态模型仍兼容后续异步执行。

## 九、自动保存与历史操作

### 9.1 本地编辑状态

画布状态变化立即更新本地 Schema，并进入 `dirty` 状态。属性表单使用短延迟写回节点，不再要求额外确认。

### 9.2 服务端自动保存

- 工作流已创建时，在最后一次变更后防抖调用现有草稿更新接口。
- 保存过程中继续允许编辑；响应只确认对应修订号，旧响应不能覆盖新状态。
- 保存失败时保留本地内容并显示重试操作。
- 新工作流在首次显式创建前只保留本地草稿，避免每次打开页面自动生成空记录。

### 9.3 撤销与重做

历史栈记录节点、边和节点配置的完整编辑快照，但不记录画布缩放、平移、选择状态和服务端运行状态。历史数量限制为 50，防止长期编辑占用过多内存。

## 十、模板

### 10.1 知识库问答

```text
开始(query) → 混合检索 → 大模型处理 → 结束(answer.text)
```

### 10.2 指定文档总结

```text
开始(documentId) → 读取文档 → 大模型处理 → 结束(summary)
```

### 10.3 主题资料汇总

```text
开始(keyword) → 文档列表 → 文本模板 → 大模型处理 → 结束(report)
```

模板创建后生成普通草稿，后续编辑、校验和发布流程与手工创建一致。

## 十一、错误处理

- Schema 解析错误：保留最后一次有效画布，原始 JSON 折叠区展示错误位置。
- 非法连接：操作时即时拒绝，并显示连接失败原因。
- 节点配置不完整：节点显示警告状态，校验和试运行前阻止提交。
- 变量路径错误：属性面板提前提示；服务端再次校验并返回具体路径。
- 自动保存失败：不丢弃本地编辑，状态变为“保存失败”，提供重试。
- Tool 401/403：节点显示权限错误，不将其伪装成无结果。
- Tool 404：显示目标资源不存在或当前用户不可见。
- Tool 超时和 Run 超时：沿用现有终态与错误码，调试抽屉展示失败节点。
- LLM Stub：在节点输出中明确显示 `stub=true`，避免误认为真实模型结果。

## 十二、安全设计

- Tool 继续使用当前 Run 用户的 Authorization，不接受工作流内自定义身份。
- 节点目录是产品能力白名单，不提供任意 URL、Header 或请求体编辑器。
- 新工具限制参数长度、分页大小和返回字段，避免批量抓取或输出过大。
- 来自文档、搜索和列表摘要的数据继续作为不可信内容传递给 LLM。
- 变量解析器只读取对象路径，不执行表达式。
- 草稿试运行仅允许工作流所有者和具备编辑权限的管理员。
- 图谱和统计节点必须在 ACL 过滤完成后才能进入 Tool Registry。

## 十三、组件边界

当前 `WorkflowCanvasEditor.tsx` 同时承担转换、画布、节点库、属性表单和状态同步。实施时按职责拆分为：

- `AgentWorkbench`：工作台布局和工作流级状态。
- `WorkflowToolbar`：工作流选择、保存状态、校验、试运行和发布。
- `NodePalette`：搜索、分组、拖拽数据源和模板入口。
- `WorkflowCanvas`：React Flow 节点、边、连接规则和布局。
- `WorkflowNodeCard`：节点摘要、配置状态和运行状态。
- `NodeInspector`：基于节点元数据渲染配置表单。
- `VariablePicker`：展示可用上游字段并生成变量表达式。
- `DebugDrawer`：Run、Step、输入输出和错误详情。
- `workflow-history`：撤销和重做状态。
- `workflow-validation`：前端线性图和节点配置校验。

Schema 转换、节点目录和运行状态映射保持纯函数，便于单元测试。

## 十四、测试与验收

### 14.1 前端测试

- Schema 与画布往返兼容旧工作流和 `uiSchema` 扩展。
- 拖拽添加、链中插入和删除中间节点。
- 非法连接被即时阻止。
- 属性修改即时写回，不需要“应用到节点”。
- 变量选择器只展示上游字段并生成合法路径。
- 撤销重做不记录视口和运行状态。
- 自动保存修订号避免旧响应覆盖新状态。
- Run Step 正确映射等待、运行、成功、失败和取消状态。

### 14.2 后端测试

- 新工具参数边界、响应裁剪、不可信数据包装和 Gateway 路径。
- VariableResolver 的字段路径、数组下标、对象类型保留和非法表达式拒绝。
- WorkflowNode 白名单包含新增工具并拒绝未知工具。
- 草稿试运行所有权、权限、定义快照、Run 来源和发布版本不变。
- 普通用户不能执行草稿 Run。
- Search / Document 双用户 ACL 在新增工具中继续成立。

### 14.3 集成验收

- 从模板创建知识库问答工作流，无需编辑 JSON 即可完成草稿试运行和发布。
- 拖入文档列表和大模型处理节点，能通过变量选择器引用列表输出。
- 非法分支、自环和孤立节点在前端和后端均被拒绝。
- 管理员可查看草稿 Run 每个节点的输入、输出、耗时和错误。
- 普通用户仍只能运行已发布版本，且无法读取其他用户不可见文档。
- frontend test、lint、build，backend 定向与全量测试，以及 Phase 7 集成门禁全部通过。
