## 一、背景与可行性结论

### 1.1 现状问题

| 问题 | 说明 |
|------|------|
| 配置分散 | `qwen.api-key` / `deepseek.api-key` / `siliconflow.api-key` / `rag.embedding.*` / `rag.rerank.*` / `kag.extraction.model` / `agent.llm.*` 散落在各模块 `application.yml` 与 Nacos `*-dev.yaml.template` |
| 密钥明文 | 所有 API Key 以明文环境变量/配置形式存在，入库（`kb_system_config`）也没有加密机制 |
| 下拉写死 | 前端模型选项大量硬编码：`EMBEDDING_PRESETS`、`CHAT_PROVIDER_OPTIONS`、`RERANK_PROVIDER_OPTIONS`、`KAG_MODEL_OPTIONS`、`AGENT_MODEL_OPTIONS`（`frontend/src/pages/admin/SettingsPage.tsx`）；唯一动态源是 `/ai/chat/models`（仅 chat 类型） |
| 热读断链 | Settings 页落库的 `qwen.model.name`、`ai.chat.provider`、`kag.extraction.model`、`agent.default-model` 在业务代码中**没有**被热读（只有 RAG TopK/rerank/milvus.host/KAG auto-extract/Agent timeout 走了 `SystemConfigCache`），改模型仍需改 Nacos + 重启 |
| 类型缺失 | 语音（TTS/STT）、图像等模型无任何配置与下拉入口 |

### 1.2 可行性结论

**完全可行，且改造面可控**。理由：

1. 基础机制已存在：`kb_system_config` 表 + `SystemConfigCache`（Redis Hash `kb:system:config`）+ `SettingsController` 分组读写（`SettingsServiceImpl.FIELD_TO_CONFIG`）已验证可用，可复用于模型库；模型库走独立表而非塞进 system config。
2. `ModelProvider`（kb-intelligence）已具备「Provider 注册 + 懒加载实例缓存 + 可用性探针」骨架，把静态 `@Value` 换成模型库动态构建即可。
3. Nacos 已接入（spring-cloud-alibaba，`config.import: optional:nacos:kb-ai-dev.yaml`），加密密钥读取有现成依赖栈；`EncryptKeyProvider` 接口预留可扩展（KMS / 环境变量 / 文件）。
4. 加密只发生在「入库写、内存读」两个点，业务使用处（`ModelProvider.getModel()` 等）不感知，改动集中在 2~3 个配置解析类。
5. 多方言 SQL（MySQL / Oracle / PostgreSQL）已有成熟模板体系（`backend/sql/schema/*`），新增两张表可对齐。

### 1.3 推荐方案（一页图）

```text
┌────────────────────────────── 管理端（kb-core-platform） ─────────────────────────────┐
│  模型管理页（前端 rabbit-admin /admin/models）                                          │
```

## 三、目标设计

### 3.1 数据模型（新增两张表）

**`kb_model_provider`（模型提供方）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK（雪花） | |
| provider_key | VARCHAR(50) UNIQUE | `qwen` / `siliconflow` / `deepseek` / `custom` / `openai` / `ollama`… |
| provider_name | VARCHAR(100) | 显示名（通义千问 / 硅基流动…） |
| base_url | VARCHAR(500) | OpenAI 兼容基址（custom 必填） |
| api_key | TEXT | **密文**（`enc:v1:...`，AES-GCM） |
| api_key_hint | VARCHAR(20) | 掩码提示（`sk-****abc`），列表回显 |
| extra_params | JSON | 预留：超时、代理等 |
| status | TINYINT | 0 禁用 / 1 启用 |
| deleted / created_at / updated_at / create_by | 标准列 | 走 `BaseEntity` 约定 |

**`kb_model`（模型条目）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK（雪花） | |
| provider_id | BIGINT FK | 关联 provider |
| model_key | VARCHAR(100) | 唯一物理模型名（`qwen3-max`、`BAAI/bge-m3`、`qwen3-rerank`…） |
| model_type | VARCHAR(20) | **`chat` / `embedding` / `rerank` / `tts` / `stt` / `image` / `other`** |
| display_name | VARCHAR(100) | 下拉显示名 |
| is_default | TINYINT | 该类型默认模型（每类型至多一个） |
| dimension | INT | embedding 维度（供检索对齐） |
| max_tokens / temperature | 预留参数列 | 或并入 `model_config` JSON |
| model_config | JSON | 预留：max_tokens / temperature / top_p… |
| status / deleted / created_at / updated_at / create_by | 标准列 | |

### 3.2 加密方案

- **算法**：AES-256-GCM（随机 12 字节 IV + 16 字节 tag），密钥 32 字节。
- **密文格式**：`enc:v1:<Base64(IV)>:<Base64(ciphertext+tag)>`，`api_key_hint` 存放明文掩码（前 3 + 后 4），列表与落库均不回显明文。
- **密钥来源（预留扩展）**：
  - 接口 `EncryptKeyProvider`：`String resolveEncryptKey()`；默认实现 `NacosEncryptKeyProvider` 读 `kb.security.encrypt-key`（Nacos / 环境变量 `KB_SECURITY_ENCRYPT_KEY` 兜底）。
  - 预留实现位：`EnvEncryptKeyProvider`、`KmsEncryptKeyProvider`（实现无需改业务代码）。
- **密钥轮换**：提供 `POST /config/models/rotate-key`（用新密钥重加密存量密文），首版可仅记录需求（任务 86）。
- **使用侧**：`kb-core-platform` 写库前加密；`kb-intelligence` / `kb-agent` 经 `ModelProviderCache`（Caffeine，TTL 60s + 主动刷新）内存解密后直接使用明文构建模型实例；**禁止**将明文写入日志、Redis、MQ。

### 3.3 运行时读取链路（kb-intelligence / kb-agent）

```text
ModelLibraryClient（Redis 缓存 → 缺失回源 kb-core 内部 API）
   ├─ ModelProvider：按 chat 类型构建 ChatLanguageModel / Streaming 实例（懒加载缓存保留）
   ├─ EmbeddingConfig：按 embedding 类型 + is_default 构建
   ├─ RerankProviderResolver：按 rerank 类型解析 model/apiKey/baseUrl（替代 @Value）
   └─ KagRuntimeSettings / Agent（kb-agent 独立 Client）：kag.extraction.model / agent.default-model 改为从模型库取
```

- 热更新：模型库变更后经 `ModelProviderCache.refresh()`（或 60s TTL 自然过期）生效，避免重启；`is_default` 变更即时影响 `getDefaultModelName()`。
- 兜底：任一环节失败（Redis 断、Nacos 缺密钥）回退现有 `qwen.api-key` / `rag.embedding.*` 等旧配置，保证滚动发布安全。

### 3.4 API 设计（kb-core-platform）

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| GET | `/config/models/types` | 模型类型枚举（chat/embedding/rerank/tts/stt/image/other + 中文名） | 登录 |
| GET | `/config/models?type=chat` | 场景下拉（启用且该类型），返回 `key/value/label/isDefault/providerKey`，**不含密钥** | 登录（场景页用） |
| GET | `/config/models/page` | 管理列表（含 api_key_hint） | systemSettings |
| POST | `/config/models` | 新增 provider/模型（api_key 密文入库） | systemSettings |
| PUT | `/config/models/{id}` | 更新（api_key 为空 = 不修改） | systemSettings |
| DELETE | `/config/models/{id}` | 删除（软删） | systemSettings |
| POST | `/config/models/test` | 连通性测试（临时解密调用 /chat/completions 或 embeddings） | systemSettings |

> 内部消费另设 `/internal/models/cache`（HMAC 签名，供 kb-intelligence / kb-agent 拉全量明文缓存）。若评审认为过度设计，可改为「Redis Hash `kb:model:cache` 直接放解密后明文 + 内部读」，二选一，任务 78 裁定。

## 五、明确不在范围内（本阶段不做）

- 不引入外部 KMS / Vault（仅预留 `EncryptKeyProvider` 扩展点，默认 Nacos 获取密钥）。
- 不删除/停用现有 `qwen.api-key`、`deepseek.api-key`、`siliconflow.api-key` 等 Nacos 配置（保持双轨兜底，滚动平滑）。
- 不实现语音/图像模型的**实际调用**（仅类型、配置、下拉能力）。
- 不做模型计费、配额、多租户模型隔离。
- 不强制要求历史 `kb_system_config` 中已落库模型字段迁移（旧键仍读，新键不重复写入）。
- 明文密钥不进入 Redis 配置缓存（`kb:system:config`）；模型库凭证只走专用链路。

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| 密钥缺失导致写库失败 | 写接口拒绝并返回明确错误；读侧回退旧配置，服务不崩溃 |
| 内存解密缓存被 dump | Caffeine 缓存仅短期持有；杜绝日志输出明文；`api_key_hint` 唯一明文出口 |
| 模型库与 Nacos 配置不一致 | 定义优先级：模型库 > Nacos 兜底；文档明示，Settings 页给出「当前来源」提示 |
| 热更新失效 | 统一走 `ModelProviderCache.refresh()` + TTL 双保险；变更接口同步触发各服务刷新（MQ 事件或 60s TTL） |
| 多方言 DDL 漂移 | 三方言 SQL 同批提交，跑 `verify-pg-schema.ps1` / `verify-oracle-schema.ps1` 校验 |
